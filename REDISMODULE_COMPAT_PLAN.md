## Context

Valkey already ships a working Redis-module compatibility mechanism, confirmed by reading the code (not assumed):

- `src/redismodule.h` is a thin alias header: `#include "valkeymodule.h"` plus `#define REDISMODULE_X VALKEYMODULE_X` / `#define RedisModule_Y ValkeyModule_Y` for every symbol it currently knows about.
- `src/module.c`'s `REGISTER_API` macro (`moduleRegisterCoreAPI()`, ~line 13011) registers every core API function under **both** `"ValkeyModule_X"` and `"RedisModule_X"` string names in `server.moduleapi`.
- Module loading (`~module.c:13460`) already accepts either `ValkeyModule_OnLoad` or `RedisModule_OnLoad` as the dlopen'd entry point.
- `VM_GetApi` (`module.c:859`) returns `VALKEYMODULE_ERR` and **leaves the target pointer untouched** when a name isn't found; `VALKEYMODULE_GET_API` (`valkeymodule.h:1546`) discards that return code. Since every `ValkeyModule_X` pointer is a zero-initialized global, an unregistered API silently resolves to `NULL` rather than aborting module load.

So the ABI-resolution machinery for "let a `RedisModule_*`-calling binary/source load into Valkey" already exists. What's missing is *header/API-surface coverage*: does Valkey actually declare and (where meaningful) implement every symbol real Redis-module code references.

Three research passes (header diff against `~/Source/redis/src/redismodule.h`, RediSearch's actual call-site footprint, and a static syntax-level compile check) converged on this picture:

- RediSearch (`~/Source/RediSearch`) vendors **Redis Enterprise's** `redismodule.h` (`#define REDISMODULE_H_ENTERPRISE` at its top), not the plain OSS one. That pulls in a materially larger surface than plain Redis.
- Of ~166 distinct `RedisModule_*` symbols RediSearch actually calls, **34 have zero Valkey counterpart at all**, and 2 have a counterpart with an incompatible signature.
- Most of the missing ones are genuinely Enterprise-only concepts (a proprietary disk-tiering "Big Store" backend, per-key `KeyMetaClass` sidecar metadata, `GetInternalSecret`) that RediSearch itself guards with `if (RedisModule_X == NULL)` runtime checks — meaning "declare the symbol, never implement it" is exactly the degradation path RediSearch already expects, matching how it already behaves against older/non-Enterprise Redis.
- A smaller set is genuinely useful OSS functionality Valkey should actually implement: the module **Config Get/Set** family (server-side config introspection) and `GetInternalSecret`. Config work is already partially started here — the current uncommitted diff in `config.c`/`module.c`/`server.h` adds `getBoolConfigFromName` + `VM_ConfigGetBool`. This plan extends that exact pattern rather than redoing it.
- One real landmine: Redis's `REDISMODULE_EVENT_CLUSTER_SLOT_MIGRATION`/`_TRIM` use event IDs 18/19, which Valkey already uses for its own, structurally different `VALKEYMODULE_EVENT_AUTHENTICATION_ATTEMPT`/`ATOMIC_SLOT_MIGRATION` events. These must **not** be aliased together — they're different features with different struct shapes. RediSearch's cluster-slot-migration integration calls a few of these (`ClusterEnableTrim`/`ClusterDisableTrim`/`ClusterPropagateForSlotMigration`) unconditionally *inside the callback Redis invokes for that specific event* — since Valkey will never fire that Redis-shaped event under that name, the callback body is unreachable dead code on Valkey, so leaving these declared-but-unimplemented is safe, not a crash risk.
- `RedisModule_ACLCheckKeyPrefixPermissions` can't be a plain `#define` alias: Redis's signature takes `(user, RedisModuleString *prefix, flags)` (3 args), Valkey's `VM_ACLCheckKeyPrefixPermissions` takes `(user, const char *key, size_t len, flags)` (4 args, different 2nd param type). Needs a small inline adapter, not a macro.

Goal of this change: extend Valkey's compat layer so RediSearch's source compiles cleanly against it, with real implementations for the handful of genuinely-useful gaps and safe NULL-pointer stubs (matching RediSearch's own defensive pattern) for the Enterprise-only remainder. Pointing RediSearch's own build at this header is an out-of-scope follow-up (its CMake has no override hook today — would need a small RediSearch-side patch); this plan covers the Valkey-side header/implementation only.

## Approach

**1. Extend real functionality in `src/module.c` / `src/valkeymodule.h` (native `ValkeyModule_*` additions)**

Confirmed by reading Redis's own implementation (`~/Source/redis/src/config.c:3584-3810`, `~/Source/redis/src/module.c:14228-14658`): the config-introspection API is a **thin, generic wrapper over the same `standardConfig`/`lookupConfig()` registry Valkey already has**, and Valkey's `config.c` already carries almost every internal helper Redis's version uses under the *same names* — `config->interface.get/set`, `performInterfaceSet`, `getModuleBoolConfig`, `getModuleNumericConfig`, `enumConfigSet`/`enumConfigGet`, the `GET_NUMERIC_TYPE` macro, `restoreBackupConfig` (this last one is already used by the in-flight `getBoolConfigFromName`). This is a near-verbatim port, not new design work. Mirror Redis's own behavior directly:

- `VM_ConfigGetNumeric`, `VM_ConfigGetEnum`, `VM_ConfigGetType`, `VM_ConfigGet` (generic string form) — port Redis's `moduleGetNumericConfig`/`moduleGetEnumConfig`/`moduleGetConfigType`/`moduleGetStringConfig` (`config.c:3622-3678`) into Valkey's `config.c` as `get*ConfigFromName` helpers alongside the existing `getBoolConfigFromName`, then thin `VM_*` wrappers in `module.c` exactly like the existing `VM_ConfigGetBool`.
- `VM_ConfigSet`/`ConfigSetBool`/`ConfigSetEnum`/`ConfigSetNumeric` — port `moduleSetBoolConfig`/`moduleSetStringConfig`/`moduleSetEnumConfig`/`moduleSetNumericConfig` (`config.c:3698-3810`, uses `getMutableConfig` + `configApply` + `restoreBackupConfig` — check whether Valkey's `config.c` already has a `getMutableConfig`-equivalent gatekeeper used by `CONFIG SET`; if named differently, reuse that instead of introducing a duplicate).
- `VM_ConfigIteratorCreate`/`Next`/`Release` — port `moduleGetConfigIterator`/`moduleConfigIteratorNext` (`config.c:3584-3620`), a straightforward `dictGetSafeIterator(configs)` walk with optional glob-pattern filtering.
- `VM_LoadDefaultConfigs` — port `RM_LoadDefaultConfigs`/`loadModuleDefaultConfigs` (`module.c:13806`, `module.c:14228`). Confirmed scope: this only applies defaults to the **calling module's own** registered configs (gated on `module->onload && !module->configs_initialized`) — it does not touch core server config or other modules, so it's self-contained module-lifecycle bookkeeping, not a generic "reset all config" operation.
- Register all of the above in `moduleRegisterCoreAPI()` via `REGISTER_API(...)` so they're reachable under both `ValkeyModule_X` and `RedisModule_X` names automatically.

**`VM_GetInternalSecret` is explicitly out of scope for this pass** — confirmed by grepping both trees: Redis's `RM_GetInternalSecret` (`module.c:14386`) returns `clusterGetSecret()`, backed by a per-cluster `internal_secret` random token generated in `cluster_legacy.c:1040` and used by Redis's own ASM (atomic-slot-migration) inter-node `AUTH`. **Valkey's cluster code has no equivalent concept at all** — this isn't a naming gap, it's a missing subsystem, and adding one is a cluster-security design decision on its own, not a header/compat-layer task. Leave this symbol unimplemented (NULL/`REDISMODULE_ERR`) for now; it only affects RediSearch's OSS-cluster-coordinator inter-shard auth path, not standalone/single-instance indexing, which is the primary use case here.

**2. Extend `src/redismodule.h` (alias/shim layer)**

- **Mechanical aliases** (~29 items): macros and type names that already have a 1:1 `VALKEYMODULE_*`/`ValkeyModule*` counterpart but are missing from the current 723-line alias file — e.g. `RedisModule_ClusterKeySlotC` → `ValkeyModule_ClusterKeySlotC` (signature-compatible, just unaliased today), plus the callback-typedef names (`RedisModuleScanCB`, `RedisModuleTypeDigestFunc`, etc.) noted by the research pass.
- **Adapter shim** for `RedisModule_ACLCheckKeyPrefixPermissions`: a small `static inline` wrapper in `redismodule.h` (same style already used for `RedisModule_Init` → `ValkeyModule_Init` in `valkeymodule.h`) that pulls `ptr`/`len` out of the `RedisModuleString *prefix` argument via `ValkeyModule_StringPtrLen` and calls `ValkeyModule_ACLCheckKeyPrefixPermissions(user, ptr, len, flags)`.
- **Declared-but-unsupported tier**: a clearly-commented new section in `redismodule.h` for the confirmed Enterprise-only symbols (`RedisModule_BigModuleRegister` and friends, `RedisModule_CreateKeyMetaClass`/`GetKeyMeta`/`SetKeyMeta`, the `RedisModule_Cluster*`/`RedisModuleSlotRange*`/`RedisModuleClusterSlotMigration*` family, `RedisModule_ShardingGetKeySlot`/`GetSlotRange`) — declare each as a statically NULL-initialized function-pointer global (or struct/typedef stand-in) local to `redismodule.h`, *not* threaded through `valkeymodule.h`'s native API-registration machinery, since these aren't real Valkey capabilities. Comment explaining why they're intentionally inert, referencing this plan's rationale (dead-code-on-Valkey / RediSearch's own NULL-guard pattern).
- Explicitly do **not** alias `REDISMODULE_EVENT_CLUSTER_SLOT_MIGRATION`/`_TRIM` or their subevents onto Valkey's `VALKEYMODULE_EVENT_ATOMIC_SLOT_MIGRATION`/`AUTHENTICATION_ATTEMPT` (ID collision, incompatible payload shapes) — give the Redis-side macros their own standalone values (matching Redis's numbering, so RediSearch's own `switch`/`case` logic against them stays internally consistent) documented as "never fired by Valkey."

**3. Files to touch**
- `src/config.c` — new `get*ConfigFromName` helpers (extends existing `getBoolConfigFromName`), config-set plumbing.
- `src/module.c` — new `VM_Config*`, `VM_GetInternalSecret` implementations + `REGISTER_API` entries in `moduleRegisterCoreAPI()`.
- `src/valkeymodule.h` — new `VALKEYMODULE_API` declarations + `VALKEYMODULE_GET_API` entries in `ValkeyModule_Init` for the above.
- `src/server.h` — forward decls for new `config.c` helpers (matches existing `getBoolConfigFromName` decl already there).
- `src/redismodule.h` — the bulk of the alias/shim/stub additions described above.
