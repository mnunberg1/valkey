## Empirical validation (2026-08-06, later same day)

**Binary load test:** loaded a real, pre-built `redisearch.so` (arm64, from a prior local RediSearch build, compiled against real Redis's `redismodule.h`) directly into Valkey via `MODULE LOAD` — not source compilation, actual ABI test. It resolved dozens of `RedisModule_*` calls via the dual-name `REGISTER_API` table and got well into config registration before failing on `RedisModule_RegisterEnumConfig` for `search-on-timeout`. Root cause: **bit 9 of the module-config flags means different things in the two projects** — `REDISMODULE_CONFIG_UNPREFIXED` in real Redis vs. `VALKEYMODULE_CONFIG_UNSIGNED` in Valkey, and Valkey has no `UNPREFIXED`-equivalent concept at any bit. This is a distinct, harder class of gap than missing symbols: flag/constant *value* drift, not just coverage. The `REDISMODULE_EVENT_CLUSTER_SLOT_MIGRATION` vs. `VALKEYMODULE_EVENT_AUTHENTICATION_ATTEMPT` ID-18 collision noted above is the same category — both projects independently allocated new bit/ID slots post-fork. There may be more; each one needs individual investigation, not a batch fix.

**Source compile test:** syntax-checked RediSearch's 5 heaviest `RedisModule_*` consumers (`module.c`, `config.c`, `doc_id_meta.c`, `notifications.c`, `spec.c`) against the updated header via a scratch copy (original `~/Source/RediSearch` checkout untouched). Two real bugs found and fixed here as a result:
1. **Missing include guard** (`src/redismodule.h` had none). The `RedisModule_ACLCheckKeyPrefixPermissions` `static inline` shim added this session isn't naturally idempotent under double-inclusion the way pure `#define` aliases are — RediSearch's `module.c` includes `redismodule.h` both directly and transitively via `document.h`, causing a hard "redefinition" error. Fixed with a standard `#ifndef`/`#define`/`#endif` guard.
2. **Pre-existing dangling aliases**, unrelated to this session's work: `REDISMODULE_SUBEVENT_REPL_BACKUP_{CREATE,RESTORE,DISCARD}` pointed at `VALKEYMODULE_SUBEVENT_REPL_BACKUP_*` macros that don't exist (the whole `REPL_BACKUP` event is dead in Valkey, marked "not used anymore"). Removed the three broken aliases rather than leave them dangling.

After both fixes: **zero compile errors in the Config API family and the ACL/ClusterKeySlotC additions** — this session's work holds up under real compilation pressure. Added 3 more confirmed-safe mechanical type aliases (`RedisModuleCmdFunc`, `RedisModuleScanCB`, `RedisModuleTimerProc`) — verified their `ValkeyModule*` counterparts actually exist before aliasing, unlike the REPL_BACKUP mistake. Checked several other candidates the compile test flagged (`REDISMODULE_CTX_FLAGS_DEBUG_ENABLED`, `_SST_RDB`, `REDISMODULE_NOTIFY_KEY_TRIMMED`, `_TRIMMED`, `REDISMODULE_OPTIONS_REQUIRE_LOADED_KEYS_IN_RAM`, `RedisModuleEvent_ReplBackup`, `RedisModuleEvent_ServerReady`) and confirmed **none** have real Valkey backing — true gaps, not mechanical aliases, correctly left undone.

Remaining compile errors are exactly the previously-known, deliberately-deferred categories: ~92 hits across Enterprise-only symbols (KeyMetaClass, Big Store, Cluster/Sharding/ASM family), plus `REDISMODULE_CONFIG_UNPREFIXED` (no Valkey concept) and `RedisModule_HashFieldMinExpire` (Redis 7.4+ hash-field-TTL introspection, no Valkey equivalent — RediSearch NULL-guards it at runtime but the symbol must still exist to compile) and the Sharding/ASM event family. None of these are new findings; all match the "deliberately not done" list above.

**One genuine (non-stub) Valkey-side change**, not just a header addition: `VALKEYMODULE_CONFIG_UNPREFIXED` added as a new flag bit (10) in `valkeymodule.h`, and `moduleVerifyConfigFlags()` in `module.c` updated to accept it. Verified: `valkey-server` builds clean; full `redismodule_compat.so` test module + tcl suite pass; full `./runtest-moduleapi` (804 tests) still passes with these additions in place.

## RedisModule_* function symbol strategy: VALKEY_REDIS_SYM_DUP / _RENAME — implemented (2026-08-12)

A real full-build attempt (not just C/C++ syntax-checking) got RediSearch's C/C++ side to 100% clean compilation against the stub tier above, but hit an architecturally different blocker in RediSearch's Rust workspace (`redisearch_rs`, ~56 files, ~46 distinct `RedisModule_*`/`RedisModuleCtx`/`RedisModuleString` references): Rust FFI bindings are generated by `bindgen`, which parses **post-preprocessor** output. Every `#define RedisModule_X ValkeyModule_X` in `redismodule.h` makes the name `RedisModule_X` vanish entirely by the time bindgen looks at the header — it only ever sees `ValkeyModule_X`. This isn't a missing-declaration problem like everything else in this doc; it's that pure textual-substitution aliasing is fundamentally invisible to any tool that doesn't run the exact same C preprocessor pass Valkey's own build does.

Fix (user-suggested): a compile-time mode switch, default `VALKEY_REDIS_SYM_DUP`, opt-out via `-DVALKEY_REDIS_SYM_RENAME` for the old pure-`#define` behavior.

- **Type aliases** (49: `RedisModuleString`, `RedisModuleCtx`, etc.) are now real `typedef`s unconditionally (mode-independent) — typedefs survive preprocessing as distinct type names, so this is strictly better with no downside, in both modes.
- **Function aliases** (373 of the original 376 — `Init`/`OnLoad`/`Assert` are structurally different, see below): in DUP mode (default), each is now a genuine independent global function-pointer symbol (mirrors `valkeymodule.h`'s own `VALKEYMODULE_API (*ValkeyModule_X)(...)  VALKEYMODULE_ATTR;` declaration style verbatim, just renamed), populated by a generated `RedisModule_Init()` wrapper: calls the real `ValkeyModule_Init()`, then copies all 373 resolved `ValkeyModule_X` pointers into their `RedisModule_X` counterparts. In RENAME mode, unchanged from before (plain `#define`).
- **`RedisModule_Init`/`OnLoad`/`Assert`** excluded from the generic treatment: `Init` needed custom codegen (the wrapper function itself, not a pointer); `OnLoad` is the module's own entry-point export (dlopen already searches both `"ValkeyModule_OnLoad"` and `"RedisModule_OnLoad"` literally — see `module.c`'s dual-name `onLoadNames[]` — so this doesn't need mode-gating either way, kept as an unconditional plain `#define`); `Assert` forwards to a function-*like macro* (`ValkeyModule_Assert(_e)`), not a plain symbol, so mode-gating is meaningless for it — also kept unconditional.
- **Event descriptors** (18: `RedisModuleEvent_FlushDB`, etc.) get the same DUP/RENAME split — `static const ValkeyModuleEvent` structs in DUP mode, `#define`s in RENAME mode.
- **Two more pre-existing dangling aliases found and fixed along the way** (same bug class as the `REPL_BACKUP` one found earlier): `RedisModuleEvent_FlushDBV2` pointed at a name that only ever existed inside a `valkeymodule.h` doc *comment* illustrating a hypothetical future naming convention — not a real symbol. Removed (no real Valkey equivalent exists — Valkey has never added a dataver-2 FlushDB payload). `RedisModuleEvent_FlushDBV1` was similarly dangling; redirected to Valkey's one real `FlushDB` event (dataver 1), which is what "V1" actually means.

Generated via a Python script (not hand-written — 373 functions made manual editing impractical and error-prone) that cross-references `valkeymodule.h`'s real `(*ValkeyModule_X)` declarations against `redismodule.h`'s existing alias list, which naturally and correctly excluded `Init`/`Assert` (no such pointer-form declaration exists for either) without a manual exclusion list. Script preserved at `/Users/mnunberg/.claude/jobs/98d7e75e/tmp/gen_redismodule_h.py` for reference/future regeneration if more aliases are added upstream (not committed to the repo — a one-off internal tool, not maintained project tooling).

**Verified end-to-end, not just "compiles":**
- `valkey-server` builds clean in both modes (this header isn't in core's include path — `module.c` never includes `redismodule.h` — so it structurally can't affect the server build).
- Hand-written `redismodule_compat.c` test module compiles clean in both DUP (default, no flags) and RENAME (`-DVALKEY_REDIS_SYM_RENAME`) modes.
- Full `./runtest-moduleapi` (804 tests) passes, including real modules (`moduleconfigs.so`, `hooks.so`, others) that call `RegisterEnumConfig`/`RegisterBoolConfig`/etc., rebuilt against the new header — confirms the generated code isn't just syntactically valid but behaviorally correct at runtime.
- **The original problem is fixed**: built RediSearch's Rust `ffi` crate against the new header in a scratch copy — `bindgen` now generates real Rust items (`pub static mut RedisModule_Alloc: ...`, `pub type RedisModuleCtx = ValkeyModuleCtx;`, 419 total `RedisModule_` occurrences in the generated bindings, versus zero before). Went further than minimum verification: also built a real downstream Rust crate (`document`) that consumes those bindings — compiled clean, not just the bindgen step.

Not yet attempted: a full link of the entire `redisearch_rs` workspace (56 files) or the whole RediSearch module end-to-end; loading a Rust-inclusive RediSearch build into a running `valkey-server` and exercising `FT.CREATE`/`FT.SEARCH`.

## Context

Valkey already ships a working Redis-module compatibility mechanism, confirmed by reading the code (not assumed):

- `src/redismodule.h` is a thin alias header: `#include "valkeymodule.h"` plus `#define REDISMODULE_X VALKEYMODULE_X` / `#define RedisModule_Y ValkeyModule_Y` for every symbol it currently knows about.
- `src/module.c`'s `REGISTER_API` macro (`moduleRegisterCoreAPI()`, ~line 13011) registers every core API function under **both** `"ValkeyModule_X"` and `"RedisModule_X"` string names in `server.moduleapi`.
- Module loading (`~module.c:13460`) already accepts either `ValkeyModule_OnLoad` or `RedisModule_OnLoad` as the dlopen'd entry point.
- `VM_GetApi` (`module.c:859`) returns `VALKEYMODULE_ERR` and **leaves the target pointer untouched** when a name isn't found; `VALKEYMODULE_GET_API` (`valkeymodule.h:1546`) discards that return code. Since every `ValkeyModule_X` pointer is a zero-initialized global, an unregistered API silently resolves to `NULL` rather than aborting module load.

So the ABI-resolution machinery for "let a `RedisModule_*`-calling binary/source load into Valkey" already exists. What's missing is *header/API-surface coverage*: does Valkey actually declare and (where meaningful) implement every symbol real Redis-module code references.

Three research passes (header diff against `~/Source/redis/src/redismodule.h`, RediSearch's actual call-site footprint, and a static syntax-level compile check) converged on this picture:

- RediSearch (`~/Source/RediSearch`) vendors **Redis Enterprise's** `redismodule.h` (`#define REDISMODULE_H_ENTERPRISE` at its top), not the plain OSS one. That pulls in a materially larger surface than plain Redis.
- Of ~166 distinct `RedisModule_*` symbols RediSearch actually calls, **34 have zero Valkey counterpart at all**, and 2 have a counterpart with an incompatible signature.
- Most of the missing ones are genuinely Enterprise-only concepts (a proprietary disk-tiering "Big Store" backend, per-key `KeyMetaClass` sidecar metadata, `GetInternalSecret`) that RediSearch itself guards with `if (RedisModule_X == NULL)` runtime checks — meaning "declare the symbol, never implement it" is exactly the degradation path RediSearch already expects, matching how it already behaves against older/non-Enterprise Redis.
- A smaller set is genuinely useful OSS functionality Valkey should actually implement: the module **Config Get/Set** family (server-side config introspection) and `GetInternalSecret`. Config work is already partially started here — the current uncommitted diff in `config.c`/`module.c`/`server.h` adds `getBoolConfigFromName` + `VM_ConfigGetBool`. This plan extends that exact pattern rather than redoing it.
- One real landmine: Redis's `REDISMODULE_EVENT_CLUSTER_SLOT_MIGRATION`/`_TRIM` use event IDs 18/19, which Valkey already uses for its own, structurally different `VALKEYMODULE_EVENT_AUTHENTICATION_ATTEMPT`/`ATOMIC_SLOT_MIGRATION` events. These must **not** be aliased together — they're different features with different struct shapes. RediSearch's cluster-slot-migration integration calls a few of these (`ClusterEnableTrim`/`ClusterDisableTrim`/`ClusterPropagateForSlotMigration`) unconditionally *inside the callback Redis invokes for that specific event* — since Valkey will never fire that Redis-shaped event under that name, the callback body is unreachable dead code on Valkey, so leaving these declared-but-unimplemented is safe, not a crash risk.
- `RedisModule_ACLCheckKeyPrefixPermissions` can't be a plain `#define` alias: Redis's signature takes `(user, RedisModuleString *prefix, flags)` (3 args), Valkey's `VM_ACLCheckKeyPrefixPermissions` takes `(user, const char *key, size_t len, flags)` (4 args, different 2nd param type). Needs a small inline adapter, not a macro.

Goal of this change: extend Valkey's compat layer so RediSearch's source compiles cleanly against it, with real implementations for the handful of genuinely-useful gaps and safe NULL-pointer stubs (matching RediSearch's own defensive pattern) for the Enterprise-only remainder. Pointing RediSearch's own build at this header is an out-of-scope follow-up (its CMake has no override hook today — would need a small RediSearch-side patch); this plan covers the Valkey-side header/implementation only.

## Approach

**1. Extend real functionality in `src/module.c` / `src/valkeymodule.h` (native `ValkeyModule_*` additions)**

Confirmed by reading Redis's own implementation (`~/Source/redis/src/config.c:3584-3810`, `~/Source/redis/src/module.c:14228-14658`): the config-introspection API is a **thin, generic wrapper over the same `standardConfig`/`lookupConfig()` registry Valkey already has**, and Valkey's `config.c` already carries almost every internal helper Redis's version uses under the *same names* — `config->interface.get/set`, `performInterfaceSet`, `getModuleBoolConfig`, `getModuleNumericConfig`, `enumConfigSet`/`enumConfigGet`, the `GET_NUMERIC_TYPE` macro, `restoreBackupConfig` (this last one is already used by the in-flight `getBoolConfigFromName`). This is a near-verbatim port, not new design work. Mirror Redis's own behavior directly:

- `VM_ConfigGetNumeric`, `VM_ConfigGetEnum`, `VM_ConfigGetType`, `VM_ConfigGet` (generic string form) — port Redis's `moduleGetNumericConfig`/`moduleGetEnumConfig`/`moduleGetConfigType`/`moduleGetStringConfig` (`config.c:3622-3678`) into Valkey's `config.c` as `get*ConfigFromName` helpers alongside the existing `getBoolConfigFromName`, then thin `VM_*` wrappers in `module.c` exactly like the existing `VM_ConfigGetBool`.
- `VM_ConfigSet`/`ConfigSetBool`/`ConfigSetEnum`/`ConfigSetNumeric` — port `moduleSetBoolConfig`/`moduleSetStringConfig`/`moduleSetEnumConfig`/`moduleSetNumericConfig` (`config.c:3698-3810`, uses `getMutableConfig` + `configApply` + `restoreBackupConfig` — check whether Valkey's `config.c` already has a `getMutableConfig`-equivalent gatekeeper used by `CONFIG SET`; if named differently, reuse that instead of introducing a duplicate).
- `VM_ConfigIteratorCreate`/`Next`/`Release` — port `moduleGetConfigIterator`/`moduleConfigIteratorNext` (`config.c:3584-3620`), a straightforward `dictGetSafeIterator(configs)` walk with optional glob-pattern filtering.
- `VM_LoadDefaultConfigs` — port `RM_LoadDefaultConfigs`/`loadModuleDefaultConfigs` (`module.c:13806`, `module.c:14228`). Confirmed scope: this only applies defaults to the **calling module's own** registered configs (gated on `module->onload && !module->configs_initialized`) — it does not touch core server config or other modules, so it's self-contained module-lifecycle bookkeeping, not a generic "reset all config" operation.
- Register all of the above in `moduleRegisterCoreAPI()` via `REGISTER_API(...)` so they're reachable under both `ValkeyModule_X` and `RedisModule_X` names automatically.

**`VM_GetInternalSecret` is explicitly out of scope for this pass** — confirmed by grepping both trees: Redis's `RM_GetInternalSecret` (`module.c:14386`) returns `clusterGetSecret()`, backed by a per-cluster `internal_secret` random token generated in `cluster_legacy.c:1040` and used by Redis's own ASM (atomic-slot-migration) inter-node `AUTH`. **Valkey's cluster code has no equivalent concept at all** — this isn't a naming gap, it's a missing subsystem, and adding one is a cluster-security design decision on its own, not a header/compat-layer task. Leave this symbol unimplemented (NULL/`REDISMODULE_ERR`) for now; it only affects RediSearch's OSS-cluster-coordinator inter-shard auth path, not standalone/single-instance indexing, which is the primary use case here.

**2. Extend `src/redismodule.h` (alias/shim layer)**

- **Mechanical aliases** (~29 items): macros and type names that already have a 1:1 `VALKEYMODULE_*`/`ValkeyModule*` counterpart but are missing from the current 723-line alias file — e.g. `RedisModule_ClusterKeySlotC` → `ValkeyModule_ClusterKeySlotC` (signature-compatible, just unaliased today), plus the callback-typedef names (`RedisModuleScanCB`, `RedisModuleTypeDigestFunc`, etc.) noted by the research pass.
- **Adapter shim** for `RedisModule_ACLCheckKeyPrefixPermissions`: a small `static inline` wrapper in `redismodule.h` (same style already used for `RedisModule_Init` → `ValkeyModule_Init` in `valkeymodule.h`) that pulls `ptr`/`len` out of the `RedisModuleString *prefix` argument via `ValkeyModule_StringPtrLen` and calls `ValkeyModule_ACLCheckKeyPrefixPermissions(user, ptr, len, flags)`.
- **Declared-but-unsupported tier**: a clearly-commented new section in `redismodule.h` for the confirmed Enterprise-only symbols (`RedisModule_BigModuleRegister` and friends, `RedisModule_CreateKeyMetaClass`/`GetKeyMeta`/`SetKeyMeta`, the `RedisModule_Cluster*`/`RedisModuleSlotRange*`/`RedisModuleClusterSlotMigration*` family, `RedisModule_ShardingGetKeySlot`/`GetSlotRange`) — declare each as a statically NULL-initialized function-pointer global (or struct/typedef stand-in) local to `redismodule.h`, *not* threaded through `valkeymodule.h`'s native API-registration machinery, since these aren't real Valkey capabilities. Comment explaining why they're intentionally inert, referencing this plan's rationale (dead-code-on-Valkey / RediSearch's own NULL-guard pattern).
- Explicitly do **not** alias `REDISMODULE_EVENT_CLUSTER_SLOT_MIGRATION`/`_TRIM` or their subevents onto Valkey's `VALKEYMODULE_EVENT_ATOMIC_SLOT_MIGRATION`/`AUTHENTICATION_ATTEMPT` (ID collision, incompatible payload shapes) — give the Redis-side macros their own standalone values (matching Redis's numbering, so RediSearch's own `switch`/`case` logic against them stays internally consistent) documented as "never fired by Valkey."

**3. Files to touch**
- `src/config.c` — new `get*ConfigFromName` helpers (extends existing `getBoolConfigFromName`), config-set plumbing.
- `src/module.c` — new `VM_Config*`, `VM_GetInternalSecret` implementations + `REGISTER_API` entries in `moduleRegisterCoreAPI()`.
- `src/valkeymodule.h` — new `VALKEYMODULE_API` declarations + `VALKEYMODULE_GET_API` entries in `ValkeyModule_Init` for the above.
- `src/server.h` — forward decls for new `config.c` helpers (matches existing `getBoolConfigFromName` decl already there).
- `src/redismodule.h` — the bulk of the alias/shim/stub additions described above.

## End-to-end success: RediSearch built, linked, loaded, and functional (2026-08-12)

Confirmed the whole chain works, not just individual pieces:

**Build**: full RediSearch C/C++ codebase and its `redisearch_rs` Rust workspace (56 files) compiled and linked into a real `redisearch.so` in scratch (17MB, valid arm64 Mach-O), against the now-committed compat header. Two build-only issues found and fixed along the way (scratch-side, then folded into follow-up decisions below):
1. **`VALKEYMODULE_API` linkage.** It defaults to empty (not `extern`), relying on GCC-style tentative-definition "common symbol" merging across translation units — fine for single-file test modules (all Valkey's own test modules are one `.c` file each), but RediSearch's many-`.c`-file `rscore` library hit 763 duplicate-symbol link errors, since Apple's `ld64` doesn't coalesce common symbols the way this relies on (confirmed not a missing `-fcommon` issue — RediSearch's CMake already passes it). Real Redis's own header avoids this by making `REDISMODULE_API` default to `extern` and only becoming a real definition in the one file that sets `REDISMODULE_MAIN` (RediSearch's `module.c` already does this, matching real Redis's convention) — a portable, standard C idiom, not something relying on linker-specific common-symbol semantics. **Not yet ported into the real Valkey header** — flagged as a separate, valuable fix (affects any multi-file Valkey module, not just RediSearch-compat) but out of scope for this session; documented here for follow-up.
2. **`struct RedisModuleCtx` bare forward-declarations.** Two RediSearch files (`coord/rmr/rmr.h`, `coord/rmr/redis_cluster.h`) forward-declare `struct RedisModuleCtx;` without including `redismodule.h`. Under the old pure-`#define` scheme this was harmless (textual substitution rewrote both the forward-decl and real uses identically), but under the new `typedef ValkeyModuleCtx RedisModuleCtx;` scheme a bare `struct RedisModuleCtx` tag is a different, incompatible type (C's tag and typedef namespaces are separate). Worked around with a scratch-side patch to those two files; not a Valkey-side header issue, and not expected to recur often (most module code either includes the header properly or doesn't forward-declare these types at all) — noted for awareness, no action taken.

**Loading into `valkey-server`**: hit and resolved two real runtime blockers in sequence, in a real running server (not just static analysis):
1. **Version gate.** RediSearch checks `INFO server`'s `redis_version` (Valkey reports a fixed `7.2.4` for compat) and refuses to load below 8.4.0. Worked around for this test via the `RS_GLOBAL_DTORS=1` env var, which RediSearch's own source uses as a leak-checking escape hatch that happens to also skip this specific check — confirmed via source reading that it has no other functional side effects (only controls whether extra shutdown-cleanup event subscriptions get registered). **Not a real fix** — production use would need a real decision about what Valkey should report here, out of scope for this session.
2. **`commandFlagsFromString()` gap — real fix, implemented.** Valkey's version of this function (`module.c`) didn't recognize two command-flag tokens real Redis's does (confirmed by diffing against `~/Source/redis/src/module.c` line-by-line): `"internal"` (real Redis: `CMD_INTERNAL|CMD_NOSCRIPT`) and `"touches-arbitrary-keys"` (real Redis: `CMD_TOUCHES_ARBITRARY_KEYS`). Any unrecognized flag token rejects the *entire* flags string, which blocked RediSearch's shard-local commands (`_FT.CREATE`, `_FT.SEARCH`, etc.) from registering at all. **Fixed as an explicit no-op per user decision**: both tokens are now recognized (registration no longer fails) but carry no enforcement — unlike real Redis, `CMD_INTERNAL` here does not hide the command from `COMMAND LIST`/`DOCS`, does not block direct client execution, and does not imply `NOSCRIPT`. This is called out in the code with a `TODO: file a Valkey issue to give CMD_INTERNAL real semantics` comment, since per RediSearch's own source comment, the *point* of the internal flag is to prevent commands like `_FT.CREATE`/`_FT.SEARCH` from bypassing ACL validation or desyncing a cluster if called directly by a regular client — accepting the flag without enforcing it leaves that gap open. This is a **known, intentional limitation** of the current fix, not an oversight.

**Result, tested live**: `MODULE LOAD` succeeds (`Module 'search' loaded from ...`). Ran directly: `FT.CREATE` (HASH index, TEXT + NUMERIC fields), `HSET` to add documents, `FT.SEARCH` (both full-text and numeric range queries — correct results), `FT.INFO` (full index stats), `FT.AGGREGATE` (GROUPBY/REDUCE), `FT.DROPINDEX` — all functioned correctly.

Full regression suite re-run after the `commandFlagsFromString` change: `./runtest-moduleapi` (804 tests) and `./runtest --single unit/introspection --single unit/introspection-2` (188 tests) both pass, no regressions.
